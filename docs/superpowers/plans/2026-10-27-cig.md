# cig: Unverified CI Blocks Landing by Default Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `oah land` never treats unverified CI as passed. Unverified, missing-required or pending CI blocks
landing by default. A user may land unverified-only CI through an explicit exception, which is recorded
beside the land record and never shown as passed. PASS means that every required check at the exact head
commit finished successfully.

**Architecture:**
- **One CI reader.** The landed reader in `src/oah/land.py` (`_check_runs`, pagination, `head_sha`
  filtering, the batch-shim refusal) gains a second endpoint through the same page loop: combined commit
  statuses at `repos/{owner}/{repo}/commits/<head>/status`. Both endpoints yield results with one shape,
  `{"position", "kind", "name", "id", "outcome"}`, plus validated raw state/conclusion fields for the
  comparison digest. `_ci_check` decides the result from those results and from the required names.
- **Assessment.** `Assessment.ready` accepts `unverified` only for the ci check, and only when a CI exception
  bound to that exact head is present. Then `code` is `OAH_LAND_READY_WITH_CI_EXCEPTION`. Without the
  exception, `failure` returns the unverified ci check, so the CLI's refusal path needs no new branch.
- **Settings.** `land.DEFAULTS = {"ci_unverified": "block", "required_checks": []}`, read from the fetched
  default branch's committed `.oah/config.toml` and validated by `land_settings`. HEAD's policy is compared
  with that target policy; it cannot enable exceptions or remove target-required checks for its own landing.
- **Push.** `push()` reads CI again under the state lock, then revalidates local authorization. A different
  result refuses, with the rechecked CI state retained in the final assessment and record. An exception is
  durably recorded before the push, with the outcome appended afterward.

**Tech Stack:** Python 3.11+ stdlib, `gh` through `oah.engines.proc` (fake `gh` in tests), real git
repositories with a local bare remote.

**Spec:** `docs/PLAN.md` 5.9 (review loop and landing), 5.13 (`land`), A21 (CI results), 8 (CI); intent `cig`
r1 in the lane brief (user decision 2026-10-27).

## Global Constraints

- Everything from the P1 and P2 plans still applies: stdlib only, never `shell=True`, UTF-8 everywhere, tests
  write inside temporary folders, `gh` and git launched through `oah.engines.proc`.
- **A17 and privacy:**
  - Check-run names and status contexts reported by GitHub never reach text, JSON or records, because they
    can be private.
  - Only names that the user wrote in `[land] required_checks` may be shown.
  - `records.jsonl` keeps holding SHAs, digests, check names, states and codes only.
  - The exception record is a separate file. It stores the repository URL with credentials removed: the
    userinfo of `scheme://` URLs, the user part of scp-style addresses, and any query or fragment.
- **Codes:**
  - `OAH_LAND_CI_UNVERIFIED`: the ci check is unverified and no exception applies.
  - `OAH_LAND_READY_WITH_CI_EXCEPTION`: the result of `--check` when an exception applies.
  - `OAH_LAND_LANDED_WITH_CI_EXCEPTION`: the result of `--merge` when the push lands with an exception.
  - Unchanged codes: `OAH_LAND_CI_PENDING` and `OAH_LAND_CI_FAILED`. `OAH_LAND_AUTHORIZATION_CHANGED` is
    reused for a CI result that changed at push time.
- **Decision order in `_ci_check`:**
  - When `gh` is missing, the check is unverified with item `gh-missing`.
  - Otherwise the latest result per `(kind, name)` decides; the highest id wins, and unnamed check runs are
    kept one by one. The order is then:
    1. Any failed result fails the check (`OAH_LAND_CI_FAILED`, even when a read was incomplete).
    2. An incomplete read is pending.
    3. Any pending result is pending.
    4. A required name with no result is unverified (`required-missing`, named).
    5. Zero results is unverified (`no-results`).
    6. Otherwise the check passed.
- **Exception scope:**
  - The exception never changes a failed or pending result.
  - The ci state stays `unverified` everywhere.
  - It binds to `Assessment.head`. `push()` already refuses when HEAD moves. A new assessment needs a new
    `--accept-unverified-ci` (or the config policy).
- Never call a GitHub write API or change branch protection.

## Review Focus

1. Can any path report `passed` or `OAH_LAND_READY` while CI is unverified? This covers `ready`, `code`,
   `failure`, the CLI text, JSON, the confirmation prompt and the records.
2. Can the exception apply to failed or pending CI, to a different head, or with an empty reason?
3. Latest-wins: a rerun that passes after a failure must pass. A failure after a pass must fail. Duplicate ids
   and unnamed runs must keep today's behaviour.
4. Statuses: the envelope `sha` must equal HEAD. Pagination and invalid JSON are refused like check runs, and
   the decoy fields (`creator.login`, `target_url`, `description`) are never exported.
5. Does any discovered name leak? Only configured required names may appear.
6. Do the exception record fields hold no credentials (URL userinfo, query)?
7. Does the push re-read refuse a changed CI result, and does it use the same destination and env as the
   assessment?

## C1 corrections

1. A refused CI recheck now shows the fresh CI state and `ready=false` in final JSON and the land record.
   The assessment retains a separate push refusal so changed passing CI remains accurately labelled passed
   while authorization is refused; a changed result invalidates the old CI exception.
2. Same-count CI replacements now refuse: a stable digest binds validated result identities, latest IDs and
   exact states/conclusions, excluding API ordering and exporting no discovered names.
3. HEAD or tracked-input changes during CI queries now refuse; the final local authorization validation
   runs after both CI endpoints under the same state lock. The fake gh mutates real checkout files/HEAD
   from its response process for portable regression coverage.
4. An unavailable or corrupt exception log now blocks before any push with
   `OAH_LAND_CI_EXCEPTION_RECORD_FAILED`. The existing atomic JSONL append fsyncs the exact-head exception
   under the state lock with the ready code before push; the later record appends the actual push outcome.
   A pre-push entry alone proves authorization was recorded, never that a push succeeded.
5. Landing now uses the fetched target's committed `[land]` policy (absent means defaults), and reports
   semantic policy differences in text, JSON and the land record (`land_policy`: target SHA, changed,
   loosened). Enabling exception mode or dropping any required name refuses with
   `OAH_LAND_POLICY_LOOSENED`, even with an explicit CI exception; policy loosening must land separately.
   Other configuration sections retain their landed behavior.
6. From an excepted assessment, newly pending, failed, differently unverified, and passing CI all refuse;
   regressions assert the remote is unchanged and final JSON/records carry each rechecked state.
