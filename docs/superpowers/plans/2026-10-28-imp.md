# imp Impact Scope Report Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `oah impact` says what it analysed, what it did not, and which checks cover the gap. Impact is
an exploration tool, not a proof (user decision 2026-10-27). An empty result is never presented as
safety.

**Architecture:**
- A new module, `src/oah/impact/scope.py`, builds the scope report beside the existing query. It reuses
  `query.query`, the gate binding rows, `count_line` and the map data. There is no second query path.
- `query.read_graph` returns the graph with a status and reason. `query.load_graph` stays as a wrapper,
  so `land` and `review` callers do not change.
- `query.ambiguous` reports the needles that `_lexical` skips. Both use one predicate,
  `query.is_ambiguous`.
- `impact_cli._query` adds `scope` and `fallback` to the JSON, and prints a scope block in the text.
  `changed_since.rerun` stays strong-only (pin and exec), so `oah land` is unchanged.

**Tech Stack:** Python 3.11+ stdlib, `unittest`, git through `oah.engines.proc` (via `mapstore._git`).

**Spec:** `docs/PLAN.md` 5.10, A11/A12; intent `imp` r1 (in the lane brief).

## Global Constraints

- Everything from the P1 plan's Global Constraints still applies: stdlib only, never `shell=True`,
  UTF-8 everywhere, a Korean one-line header on new `.py` files, test writes inside temp folders.
- **Layers and statuses.** The scope report lists five layers: `gates`, `lexical`, `db`, `graph` and
  `cochange`. Wiki rows come from the lexical search, so `wiki` is not a separate layer. Each layer has
  a `status` and a `reason`. The status is one of:
  - `analysed`: it ran on fresh inputs.
  - `unavailable`: it had nothing to read. Examples: no gate ledgers, no SQL migrations, or a missing or
    unreadable graph file.
  - `stale`: its inputs are older than the commit queried. Examples: a graph recording another commit,
    or a default-branch map from the last fetch.
  - `stale-unknown`: the graph carries no commit identity that can be checked. It is never guessed fresh.
  - `skipped`: it does not apply. Examples: only DB entities were queried, or nothing was selected.
- **Graph identity.** The graph is fresh only when `graph.json` records a full hex commit id at
  top-level `commit` or at `graph.commit` (networkx node-link attributes), and that id equals the
  queried commit. A different id is `stale`. No id, or a value that is not a full hex id, is
  `stale-unknown`.
- **Default branch.** A stale default-branch map makes `lexical`, `db` and `cochange` `stale` when they
  would otherwise be `analysed`. An unavailable default branch (for example, no remote) does not change
  the layers; the existing warning already says so.
- **`depth` is 1.** This lane adds no multi-hop tracing (non-goal).
- **`complete`** is true only when all five layers are `analysed`, no name was skipped as ambiguous and
  no likely rename or map coverage gap was found. Both maps' excluded paths and unparsed SQL regions
  are gaps even when every layer ran fresh. The fixed dynamic-path note is a permanent caveat, not a
  skip, so it does not make the result incomplete by itself.
- **Unanalysed list** (`scope.unanalysed`, in this order):
  1. Ambiguous names, one item per (target, name) pair, with the number of files sharing the name and
     the `max_ambiguity` limit.
  2. Each layer that is neither `analysed` nor `skipped` (`kind: "layer"`), in layer order, with its
     status and reason. A missing, unreadable, stale or unverifiable graph appears here.
  3. Coverage gaps from each map (`kind: "excluded-path"` or `"sql-unparsed"`), with the map name,
     file and, for SQL, line and reason. Each item says how to follow up.
  4. Likely renames. These are only computed with `--changed-since`. They come from git's `-M` pairs
     (with a similarity percentage) plus deleted/added pairs with the same file name (similarity
     `null`), untracked files included. Differently named untracked files are also compared with the
     deleted blobs using hashes of normalized byte lines first, so unchanged renames (including CRLF
     checkouts of LF blobs) are recognized at any size. For nonmatching hashes, both files must be at
     most 256 KiB; line-set Jaccard similarity of at least 50% reports a likely rename with an integer
     percentage. Hashes and line sets are computed once per file. Larger nonmatching pairs appear as
     `possible-rename-unchecked` in the unanalysed list, making the report incomplete and enabling
     fallback checks. This is a bounded, linear-in-file-size heuristic, not git's score.
     Content comparisons reuse the map's path check to avoid following symlinks outside the tree.
  5. Always last: the fixed note that dynamic calls, reflection and string-built paths are not traced.
- **No false safety.** An empty result prints
  `nothing found in the analysed scope; this is not proof of no impact`, followed by the unanalysed
  list. The text `no references found` is gone. No field or message calls a result safe.
  `scope.summary` holds the same sentence, or a count sentence when rows exist.
- **Fallback checks** are computed only when `complete` is false.
  - They are labelled `binding: "fallback"` and kept separate from the strong `rerun` list. A gate
    already in the strong plan is not repeated.
  - **Gate fallback.** A ledger references a file target when any of its gates' CHECK or EXPECT text
    names one of the target's needles:
    - the target's parent folder path (`src/pkg`) or its dotted form (`src.pkg`);
    - the target's dotted module name without the extension, down to its last two segments
      (`src.pkg.mod`, `pkg.mod`), or the sole segment of a root-level module (`alpha` for `alpha.py`).

    Then every gate of that ledger is included. Replace backslashes with `/` in the whole raw CHECK
    and EXPECT text and search it directly, with spaces inside a needle matched literally. Both
    sides must be the start/end of text, `/`, the existing dotted-module separator `.`, or a ledger
    delimiter (whitespace, quotes, parentheses, commas, semicolons, `=` or `:`). Thus `src/pkg`
    matches `./src/pkg/x.py` but not `src/pkgs`. No tokenization, quote parsing, shell expansion or
    command execution is used. A plain directory name can conservatively add fallback checks;
    top-level files have no folder needle.
  - **Configured fallback.** `[impact] fallback_checks = []` holds an array of strings. Each one is
    added as a check with `source: "[impact] fallback_checks"` for any selected targets, including
    DB entities. Only folder/module-based gate discovery requires file targets.
  - **Where it appears.** The JSON top-level `fallback` covers all targets, and
    `changed_since.fallback` covers the changed files. The text prints `re-run (fallback): ...` lines.
- **Config.** `fallback_checks` goes through `oah.impact.defaults.DEFAULTS`, is validated as an array
  of strings, and is not a map key. Unknown keys still refuse.
